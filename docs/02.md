# Chapter 2 - TCP and Streams

## The First Networking Illusion

Most programmers approach networking with an assumption so natural that they rarely question it.

Imagine the following code:

```javascript
socket.write('Hello');
```

The intuitive expectation is simple:

1. One message was sent.
2. One message will arrive.
3. The receiver will get exactly `"Hello"`.

This mental model appears reasonable.

It is also wrong.

Not slightly wrong.

Fundamentally wrong.

The moment we begin building networked software, we must abandon this assumption entirely.

Because TCP does not understand messages.

TCP only understands bytes.

This realization marks one of the first major shifts in a programmer's understanding of distributed systems.

---

# Understanding the Journey of Data

When a program sends information across a network, the operating system does not think in terms of:

```txt
Messages
Chats
Files
Commands
```

Instead, it sees:

```txt
01001000
01100101
01101100
01101100
01101111
```

A sequence of bytes.

Nothing more.

The word:

```txt
Hello
```

has no special meaning.

To TCP, it is simply a collection of binary values.

The protocol's responsibility is not to understand what those bytes represent.

Its responsibility is only to transport them from one machine to another reliably.

---

# What TCP Actually Promises

TCP stands for:

```txt
Transmission Control Protocol
```

Its purpose is to provide reliable communication between two endpoints.

When programmers hear the word "reliable," they often assume:

```txt
Reliable = Message Based
```

This is incorrect.

TCP guarantees:

- Data arrives.
- Data arrives in order.
- Data is not duplicated.
- Corrupted packets are retransmitted.

TCP does not guarantee:

- Message boundaries.
- Message sizes.
- Application-level meaning.

This distinction is critical.

---

# Streams, Not Messages

TCP is a stream protocol.

The easiest analogy is a river.

Imagine two cities connected by a river.

One city drops wooden logs into the water.

The other city receives wooden logs downstream.

The river does not care where one shipment ends and another begins.

It only moves a continuous flow of objects.

TCP behaves similarly.

When we execute:

```javascript
socket.write('Hello');
socket.write('World');
```

We might expect:

```txt
Hello
World
```

to arrive separately.

But TCP may deliver:

```txt
HelloWorld
```

in a single chunk.

Or:

```txt
He
lloWo
rld
```

in multiple chunks.

Both outcomes are perfectly valid.

TCP has not failed.

It has behaved exactly as designed.

---

# Why This Happens

The operating system continuously optimizes network traffic.

Sending a packet across a network involves overhead.

Therefore, the OS may decide to:

- Merge writes together.
- Split writes apart.
- Delay transmission briefly.
- Repackage data.

All without informing your application.

The operating system is not trying to make your life difficult.

It is trying to maximize efficiency.

The unfortunate side effect is that application developers must solve an additional problem.

---

# The Message Boundary Problem

Suppose we send two chat messages:

```txt
Hello
How are you?
```

The receiver might observe:

```txt
HelloHow are you?
```

How can the receiver determine where one message ends and another begins?

TCP offers no answer.

This becomes our responsibility.

This problem is known as:

```txt
Message Framing
```

Framing is the process of defining message boundaries within a byte stream.

Every application protocol must solve this problem somehow.

---

# How Real Protocols Solve Framing

Different protocols use different strategies.

## Fixed-Length Messages

Some protocols define:

```txt
Every message is exactly 128 bytes.
```

Simple.

But wasteful.

Most messages are smaller.

---

## Length Prefix

Many modern protocols send:

```txt
Message Length
Message Content
```

Example:

```txt
5|Hello
```

The receiver first reads the number:

```txt
5
```

Then reads exactly five bytes.

This approach is extremely common.

---

## Delimiter-Based Framing

This is the strategy we used in Isimud.

Every message ends with:

```txt
\n
```

Example:

```txt
{"message":"hello"}\n
{"message":"world"}\n
```

The receiver reads until it encounters the delimiter.

This approach is easy to implement and perfect for learning.

---

# The Birth of Application Protocols

At this point, an important realization emerges.

TCP solves transportation.

It does not solve communication.

Those are different problems.

Imagine a postal service.

The postal service can deliver envelopes.

But it does not know:

- Whether the envelope contains a contract.
- A love letter.
- A tax form.
- A resignation notice.

The postal service merely transports.

Meaning is added by humans.

Similarly:

TCP transports bytes.

Meaning is added by application protocols.

---

# Designing Our Own Protocol

As Isimud evolved, we introduced structured messages.

Instead of sending:

```txt
Hello
```

we send:

```json
{
  "id": "...",
  "version": 1,
  "type": "chat_message",
  "from": {
    "nodeId": "...",
    "username": "Ali"
  },
  "payload": {
    "body": "Hello"
  },
  "timestamp": "..."
}
```

This structure forms our protocol.

A protocol is simply:

> An agreement about how information should be represented and exchanged.

Every participant follows the same rules.

Without agreement, communication becomes impossible.

---

# Why JSON?

We selected JSON because:

- Human-readable.
- Easy to debug.
- Widely supported.
- Flexible.

Most importantly, JSON allows protocols to evolve.

Today's message might contain:

```json
{
  "body": "Hello"
}
```

Tomorrow it may include:

```json
{
  "body": "Hello",
  "encrypted": true,
  "signature": "..."
}
```

Without redesigning the entire system.

---

# Protocol Versioning

One of the first fields we introduced was:

```json
{
  "version": 1
}
```

At first glance, this seems unnecessary.

Why add complexity now?

Because protocols live longer than code.

Imagine Version 2 introduces encryption.

Older peers will not understand the new format.

Version numbers allow systems to evolve while remaining compatible.

Large-scale systems rely heavily on versioning.

Without it, upgrades become dangerous.

---

# Parsing: Transforming Bytes Into Meaning

Once raw bytes arrive from TCP, we must transform them into meaningful structures.

This responsibility belongs to:

```txt
MessageParser
```

The parser acts as a translator.

Input:

```txt
Raw bytes
```

Output:

```txt
Application messages
```

Without a parser, the application would need to understand networking details everywhere.

That would create tight coupling and architectural chaos.

---

# Validation: Trust Nothing

One of the most important principles in network programming is:

> Never trust incoming data.

Not because other users are malicious.

But because networks are messy.

Messages may be:

- Corrupted.
- Truncated.
- Outdated.
- Malformed.

For this reason, Isimud introduced:

```txt
MessageValidator
```

before accepting incoming messages.

Validation acts as a security checkpoint between the network and the application.

---

# The Layering Principle

As Isimud grew, we began separating responsibilities.

Instead of putting everything inside TcpTransport, we created layers.

```txt
CLI Layer
    ↓
Application Layer
    ↓
Protocol Layer
    ↓
Transport Layer
```

Each layer solves a different problem.

The transport layer moves bytes.

The protocol layer understands messages.

The application layer understands users.

This separation is one of the most important architectural ideas in software engineering.

---

# A Mental Model for the Future

Whenever data moves through Isimud, imagine the following journey:

```txt
User types text
        ↓
Command
        ↓
MessageFactory
        ↓
JSON Message
        ↓
TcpTransport
        ↓
TCP Stream
        ↓
Network
        ↓
Remote TCP Stream
        ↓
MessageParser
        ↓
MessageValidator
        ↓
Application Logic
        ↓
Displayed to User
```

Every future feature we build will follow this path.

Encryption.

File transfer.

Group messaging.

Persistence.

All of them.

Understanding this pipeline is the key to understanding the rest of the system.

---

# Chapter Summary

In this chapter we learned a lesson that surprises almost every programmer:

> TCP does not understand messages.

TCP understands only streams of bytes.

Because of this, every networked application must solve additional problems:

- Message framing
- Protocol design
- Parsing
- Validation

These responsibilities belong to the application, not the transport protocol.

With this foundation established, we are finally ready to explore the next challenge:

If TCP only transports data, how do independent devices discover one another on a network where nobody knows who is online?

The answer leads us into the world of UDP, broadcasting, and service discovery.
