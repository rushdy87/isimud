# Chapter 3 - Message Framing

## The Problem That Should Not Exist

At first glance, message boundaries seem obvious.

A user types:

```txt
Hello
```

The application sends:

```txt
Hello
```

The receiver reads:

```txt
Hello
```

Simple.

Or at least it appears simple.

After all, humans naturally think in terms of messages.

We send emails.

We send text messages.

We send letters.

We speak in sentences.

Every form of communication we encounter in daily life has boundaries.

A sentence begins.

A sentence ends.

A letter begins.

A letter ends.

A conversation begins.

A conversation ends.

Our brains are trained to see communication as a sequence of discrete units.

Computers are not.

The network sees something entirely different.

It sees only a continuous stream of bytes.

The consequence is profound:

> Messages do not naturally exist on a TCP connection.

We must invent them.

---

# The River Analogy Revisited

In the previous chapter, we described TCP as a river.

Let us push that analogy further.

Imagine standing beside a river while someone upstream drops objects into the water:

```txt
Package A
Package B
Package C
```

Downstream, you receive:

```txt
Package A + Package B together
```

Or:

```txt
Half of Package A
```

followed later by:

```txt
The rest of Package A
Package B
Half of Package C
```

The river does not preserve package boundaries.

It preserves flow.

TCP behaves exactly the same way.

A TCP connection is not a sequence of messages.

It is a sequence of bytes.

The concept of a message exists only inside the application.

---

# The Missing Information

Suppose we send two chat messages:

```txt
Hello
How are you?
```

The sender knows there are two messages.

The receiver does not.

The receiver might observe:

```txt
HelloHow are you?
```

How can it determine:

```txt
Hello
```

is one message and:

```txt
How are you?
```

is another?

The answer is:

It cannot.

Not without additional information.

This missing information is called:

```txt
Framing
```

---

# What Is Message Framing?

Message framing is the process of defining where one message ends and another begins.

More formally:

> Message framing is the mechanism by which an application reconstructs logical messages from a continuous stream of bytes.

This is one of the most fundamental problems in network programming.

Every protocol must solve it.

No exceptions.

---

# Why TCP Does Not Solve Framing

A common question arises:

> Why doesn't TCP simply include message boundaries?

The answer lies in its design philosophy.

TCP was built to solve a specific problem:

```txt
Reliable byte transport
```

Nothing more.

The protocol intentionally avoids making assumptions about application data.

TCP does not know whether the bytes represent:

```txt
A chat message
A photograph
A video stream
A database query
An encrypted file
```

Therefore TCP remains neutral.

It transports bytes.

Applications define meaning.

This separation of responsibilities is one of the reasons TCP has remained successful for decades.

---

# Framing Strategies

Throughout the history of networking, engineers have developed several approaches to framing.

Each has strengths and weaknesses.

---

# Strategy 1: Fixed-Length Messages

The simplest approach is to decide:

```txt
Every message is exactly 256 bytes.
```

A receiver reads:

```txt
256 bytes
```

and immediately knows that a complete message has arrived.

Simple.

Fast.

Easy to implement.

Unfortunately, it wastes enormous amounts of bandwidth.

Suppose the user sends:

```txt
Hi
```

Two bytes of useful information.

Two hundred fifty-four bytes of wasted space.

For this reason, fixed-length protocols are uncommon in modern application design.

---

# Strategy 2: Length-Prefixed Messages

Instead of defining a fixed size, we transmit the message length first.

Example:

```txt
5:Hello
```

The receiver reads:

```txt
5
```

and knows exactly how many bytes belong to the message.

This approach is used extensively in high-performance systems.

Many binary protocols employ this strategy.

Examples include:

- Protocol Buffers
- gRPC
- Many database protocols
- Numerous game networking protocols

Length-prefixed framing is efficient and scalable.

However, it requires more careful implementation.

---

# Strategy 3: Delimiter-Based Framing

Instead of sending the message length, we define a special marker that indicates the end of a message.

For example:

```txt
Hello\n
How are you?\n
```

The receiver continues reading until it encounters:

```txt
\n
```

At that moment, it knows the message is complete.

This strategy is extremely popular because it is simple.

Many text-based protocols use delimiters.

Examples include:

- IRC
- SMTP
- POP3
- Early HTTP headers

And, importantly:

- Isimud

---

# Why Isimud Uses Delimiter-Based Framing

When designing Isimud, we had several goals:

1. Simplicity
2. Readability
3. Educational value

A length-prefixed protocol would be more robust.

But it would also introduce additional complexity.

The newline delimiter:

```txt
\n
```

offers an elegant compromise.

Every message becomes:

```txt
{"type":"chat_message"}\n
```

The parser simply splits incoming data using:

```javascript
rawData.split('\n');
```

The implementation is easy to understand.

And understanding is more valuable than optimization at this stage.

---

# Framing Is Not Parsing

This distinction is subtle but important.

Consider:

```txt
{"message":"hello"}\n
```

Finding:

```txt
\n
```

is framing.

Converting:

```txt
{"message":"hello"}
```

into a JavaScript object is parsing.

These are separate responsibilities.

Framing answers:

> Where does the message end?

Parsing answers:

> What does the message mean?

Many beginners accidentally merge these concepts.

Professional systems keep them separate.

---

# Framing Before Meaning

Notice the order of operations:

```txt
TCP Stream
↓
Framing
↓
Parsing
↓
Validation
↓
Application Logic
```

This order is not arbitrary.

It is essential.

Before we can understand a message, we must know where it ends.

Before we can validate a message, we must parse it.

Before application logic can execute, the data must be validated.

Each step depends on the previous one.

This is a recurring pattern throughout software architecture.

---

# The Hidden Bug in Our Current Implementation

At first glance, Isimud's framing implementation appears sufficient.

We send:

```txt
JSON + '\n'
```

and split on:

```txt
'\n'
```

Problem solved.

Or is it?

Consider this situation:

A large JSON message is transmitted.

TCP delivers only half of it:

```txt
{"type":"chat_mes
```

No delimiter has arrived yet.

The message is incomplete.

A robust protocol should buffer the partial data and wait for more bytes.

Our current implementation does not do this.

Instead, it assumes every chunk contains complete messages.

For small messages in a local network, this usually works.

For larger systems, it becomes dangerous.

This observation reveals an important lesson:

> Most networking code appears correct until real-world conditions expose its assumptions.

---

# The Concept of a Buffer

Professional networking software introduces a buffer.

Instead of processing data immediately, it stores incoming bytes temporarily.

Example:

```txt
Incoming chunk:
{"type":"chat_mes
```

Buffer becomes:

```txt
{"type":"chat_mes
```

Later:

```txt
sage"}\n
```

Arrives.

Buffer becomes:

```txt
{"type":"chat_message"}\n
```

Only now can framing occur safely.

This technique is fundamental to reliable protocol implementations.

We will eventually introduce buffering into Isimud.

---

# Framing as a Contract

One of the most useful ways to think about framing is as a contract.

The sender promises:

```txt
I will terminate every message with '\n'
```

The receiver promises:

```txt
I will treat '\n' as the end of a message
```

Both sides agree.

Communication becomes possible.

This is the essence of protocol design.

A protocol is not magic.

A protocol is merely an agreement.

---

# A Broader Lesson

Message framing illustrates a larger truth about software engineering.

Many concepts that seem natural are actually inventions.

Messages are invented.

Users are invented.

Files are invented.

Databases are invented.

At the lowest level, computers manipulate bytes.

Everything else is abstraction.

Software engineering is the art of creating useful abstractions on top of simpler realities.

Message framing is one of the first places where this truth becomes visible.

---

# Chapter Summary

In this chapter we explored one of the most fundamental challenges in network programming:

> How do we find message boundaries in a stream that contains no boundaries?

We learned that:

- TCP transports streams, not messages.
- Applications must define message boundaries themselves.
- This process is called framing.
- Common framing strategies include fixed-length, length-prefixed, and delimiter-based protocols.
- Isimud currently uses newline-delimited framing.
- Framing and parsing are separate responsibilities.
- Real-world systems often require buffering to handle partial messages safely.

Most importantly, we discovered that messages are not provided by the network.

They are created by protocol design.

In the next chapter, we will build upon this idea and explore an even deeper question:

If messages can be represented in countless ways, how do independent systems agree on a common structure and meaning?

To answer that question, we must begin designing protocols.
