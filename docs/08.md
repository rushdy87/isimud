## Chapter 8: The Command Pattern

> _"A program begins to grow old the moment it starts asking itself too many questions."_

### Introduction: The Quietly Growing Monster

In the previous chapters, we learned how to make parts of our system communicate through Event-Driven Architecture. Components no longer needed to know about each other directly. They simply announced that something had happened, and interested parties reacted.

But while we were solving network coupling, another kind of coupling was quietly growing inside our application.

As Isimud gained more features, our `CommandHandler` started to accumulate heavy responsibilities. Users interact with the terminal using commands like `/peers`, `/connect-peer`, `/send-to`, and `/help`.

At first, handling these commands looked entirely innocent:

```javascript
if (command === '/peers') {
  // Logic to show peers
} else if (command === '/connect-peer') {
  // Logic to connect to a new peer
} else if (command === '/send-to') {
  // Logic to send a message
}
```

Then, more commands inevitably arrived:

```javascript
else if (command === "/groups") {
  // ...
}
else if (command === "/file") {
  // ...
}
else if (command === "/encrypt") {
  // ...
}

```

Suddenly, our simple handler became the receptionist, manager, secretary, and janitor of the entire application. Just like a rigid bureaucratic system collapses under the weight of severe centralization—where one entity is forced to process every detail—software systems collapse when a single file handles all logic.

This chapter is about preventing that dystopian future.

---

### The Growing Monster: The Restaurant Analogy

Imagine a restaurant. A customer says: _"I want coffee."_

If the waiter (who takes the input) also had to:

1. Grind the beans,
2. Boil the water,
3. Prepare the coffee,
4. Wash the dishes,
5. Take the payment...
   The restaurant would quickly collapse into chaos.

A waiter should only know: **"Someone wants coffee. Who can prepare it?"**
Software suffers from the exact same problem. A component should know **what** needs to happen. It should not know **how** everything happens.
This is the essence of the **Command Pattern**.

---

### What Is a Command?

A command is an object that encapsulates a request as an object.
Instead of writing a function and executing it immediately:

```javascript
connectPeer(username);
```

We create an object that _represents_ the action:

```javascript
const command = new ConnectPeerCommand(username);
```

And then we ask it to execute itself (each command class has an `execute()` method):

```javascript
await command.execute();
```

The action becomes a first-class object. This sounds like a simple syntax change, but it alters the architecture dramatically.
In JavaScript, functions are already first-class citizens. The Command Pattern is not about replacing functions. It is about giving actions identity, state, and structure.

---

### Encapsulating Behavior

**Without commands:**
Input ⟵ Big Handler ⟵ Many `if/else` statements ⟵ Business Logic.

**With commands:**
Input ⟵ Command Resolver ⟵ Command Object ⟵ `execute()`.

The handler no longer performs the work. It **delegates**.

---

### Why Do We Need This?

#### Reason 1: Open for Extension

Suppose we want to add a `/groups` feature.

- **Without commands:** We must open the giant `CommandHandler`, add another `else if`, modify existing code, and risk breaking something else.
- **With commands:** We simply create a new `GroupsCommand` class and register it. Done. No existing code is touched.
  This perfectly follows the **Open/Closed Principle**: Software should be open for extension, but closed for modification.

#### Reason 2: Separation of Responsibilities

A `PeersCommand` should know how to display peers. A `ConnectPeerCommand` should know how to connect to peers. No single command should know everything. This enforces the Single Responsibility Principle.

#### Reason 3: Better Testing

Testing a massive `if/else` chain inside one file is extremely difficult.
Testing this:

```javascript
const command = new ConnectPeerCommand(peerService, 'Ali');
await command.execute();
```

Is incredibly easy. Each command becomes an isolated, testable unit.

---

### The Structure and Code

A common folder structure looks like this:

```text
commands/
│
├── Command.js              (The Base Contract)
├── PeersCommand.js         (Displays peers)
├── ConnectPeerCommand.js   (Connects to a peer)
├── SendToCommand.js        (Sends messages)
└── HelpCommand.js          (Displays help)

```

**The Base Command:**
This is our contract. Every command class must implement the `execute()` method.

```javascript
export class Command {
  async execute() {
    throw new Error('execute() not implemented');
  }
}
```

**Example: `PeersCommand**`

```javascript
export class PeersCommand extends Command {
  constructor(peerRegistry) {
    super();
    this.peerRegistry = peerRegistry;
  }

  async execute() {
    const peers = this.peerRegistry.getAll();
    for (const peer of peers) {
      console.log(peer.username);
    }
  }
}
```

**Example: `ConnectPeerCommand**`

```javascript
export class ConnectPeerCommand extends Command {
  constructor(peerService, username) {
    super();
    this.peerService = peerService;
    this.username = username;
  }

  async execute() {
    await this.peerService.connect(this.username);
  }
}
```

**Notice something important:** The command does not know about TCP, Sockets, Discovery, or Registries. It only knows: _"I need to connect this user."_ Everything else is elegantly delegated.

---

### The Invoker

Someone still needs to trigger these commands. This role is called **The Invoker**.
In Isimud, the flow is:
Terminal Input ⟵ `CommandHandler` (Invoker) ⟵ Command Object ⟵ `execute()`.

The `CommandHandler` becomes remarkably small:

```javascript
const command = factory.create(input);

if (!command) {
  console.log('Unknown command');
  return;
}

await command.execute();
```

Its job is no longer to understand every feature. Its job is simply to: Receive, Resolve, and Execute.

---

### The Command Factory

Eventually, we need a place that maps raw text into command objects.

- `"/peers"` ⟵ maps to ⟵ `PeersCommand`
- `"/connect-peer Ali"` ⟵ maps to ⟵ `ConnectPeerCommand`

This responsibility belongs to the **Command Factory**. The factory is the only component that decides which command object to build based on the user's input string.

---

### A New Mental Model

- **Without commands:** Input triggers Logic.
- **With commands:** Input creates an Object, and the Object holds the Behavior.

Actions become _things_. And once actions become objects, fascinating possibilities emerge:

- We can queue commands.
- We can log commands to a file.
- We can retry commands if they fail.
- We can undo commands.
  Entire distributed systems are built around this exact concept.

---

### Architecture After the Refactor

By applying the Command Pattern, Isimud ensures that adding new features (like `/create-group` or `/send-file`) does not turn our terminal handler into a giant labyrinth of conditional statements. Every feature receives its own clean room instead of sleeping on the living room floor.

**The Clean Flow:**
Terminal ⟵ `CommandHandler` ⟵ `CommandFactory` ⟵ `Command` ⟵ Application Services ⟵ Domain Objects.

Each layer has one clear responsibility. Each layer knows only what it absolutely needs to know. This is how complexity is tamed.

---

### Key Takeaways

- A command is an object representing a specific action.

- Commands encapsulate behavior and separate it from the interface.
- Commands reduce coupling and massively improve extensibility.
- The handler (`CommandHandler`) becomes an "invoker" rather than an absolute decision-maker.

- The factory creates commands from user input.
- The Command Pattern prepares Isimud for safe, structured future growth.
