## Chapter 6: Event-Driven Architecture — When Dependencies Begin to Spread

### Introduction: The Core Dilemma

In the previous chapter, we identified the two great enemies of software systems:

1. **Complexity**
2. **Coupling**

We discovered that complexity is inevitable. As systems grow, they naturally become larger and more sophisticated. The real danger lies in _coupling_. When components become tightly connected, every modification becomes risky. A small change in one part of the system can ripple throughout the entire application.

This observation leads us to a critical engineering question:
**How can independent parts of a system cooperate without becoming dependent on one another?**
One of the most powerful answers to this question is Event-Driven Architecture (EDA).

---

### The Traditional Approach: The Dependency Explosion

Imagine a simple chat application. A new message arrives from the network. Several things must happen consecutively:

1. Display the message on the UI.
2. Update the peer's state.
3. Write a log entry.
4. Store the message in a database.
5. Trigger user notifications.

A straightforward implementation might look like this:
Network Layer ⟵ directly calls ⟵ UI, Logger, Storage, and Notifications.

At first, this seems perfectly reasonable. The application works, and the code is highly traceable. The problem emerges as the system grows.

#### The Birth of the "God Object"

Suppose we introduce a new feature: Analytics.
Now the network layer must also notify the analytics system.
Later we add: Message Archiving. Another dependency appears.
Then: Performance Monitoring. Another dependency.

Eventually, the network layer—which should only care about moving bytes—becomes aware of nearly every component in the system. It evolves into what some engineers call **The God Object**: a component that knows too much and controls too much. This dramatically increases coupling.

---

### The Hidden Cost of Direct Communication

Direct communication feels simple because it is visible. We see `Component A` calling `Component B` and believe the relationship is harmless.
The problem is cumulative. Imagine:

- A depends on B
- A depends on C
- A depends on D
- A depends on E

Now, every modification to A carries the risk of affecting four other systems. As the number of dependencies grows, understanding the execution path becomes increasingly difficult. The software begins to resemble a **spider web**. Touch one thread, and the entire structure vibrates.

---

### An Alternative Perspective: Broadcasting

What if Component A did not need to know who was listening?
What if it simply announced: **"A message has arrived"** and allowed interested components to react on their own terms?

This idea changes everything. Instead of direct communication:
A ⟵ calls ⟵ B, C, D

We obtain:
A ⟵ emits ⟵ **Event** ⟵ listened to by ⟵ B, C, D

Component A no longer knows about B, C, or D. It merely publishes information. The interested parties decide whether they want to react. This is the essence of Event-Driven Architecture.

---

### What Is an Event?

An event represents something that happened. Not something that _should_ happen, but something that _already_ happened in the past.
Examples:

- `message:received`
- `peer:connected`
- `network:error`

Notice the wording. Events describe **facts**, not **commands**.
For example, `message:received` means: "A message has been received." It does not mean: "Display the message." Those are two entirely different concepts. This distinction is extremely important.

#### Events vs. Commands

Many beginners confuse events and commands.

- **A Command says:** Do this. (Examples: `SendMessage`, `ConnectPeer`). Commands represent _intentions_ for the future.
- **An Event says:** This happened. (Examples: `MessageSent`, `PeerConnected`). Events represent _historical facts_.

The distinction may seem subtle, but it becomes crucial in larger systems. Commands ask for an action; events report history.

---

### Thinking in Events in Isimud

Consider the following scenario: A peer connects to the Isimud application.

**In a traditional design:**
`TcpTransport` explicitly calls `PeerRegistry` and `Logger`. The transport layer is managing the other components.

**In an event-driven design:**
`TcpTransport` emits `peer:connected`... and stops.
Its responsibility ends there. Other components decide independently whether they care about this occurrence. This dramatically reduces coupling.

---

### Introducing the Event Bus: The Airport Analogy

To implement event-driven communication, systems often use a central mechanism called an **Event Bus**. The Event Bus acts like a public announcement system.

Imagine an airport. When a gate changes for a flight, the airport staff does not walk around informing every passenger individually. Instead, they broadcast over the speakers: _"Flight 123 has moved to Gate B12."_
Anyone interested (passengers of that flight) listens and moves. Anyone uninterested ignores it. The airport does not need to know who is listening.
An Event Bus works exactly the same way.

#### Event Producers and Consumers

Within an event-driven system, there are two major roles:

1. **Producers:** They generate events. In Isimud, a component like `TcpTransport` observes a network action and publishes an event.
2. **Consumers:** They react to events. Components like `PeerRegistry` or the UI subscribe to events and perform actions when those events occur.

---

### Loose Coupling Through Events

Imagine a new requirement appears. We want to count the total number of incoming messages.

- **Without events:** `TcpTransport` must be opened and modified.
- **With events:** A new `MessageCounter` component simply subscribes to `message:received`. No changes to the transport layer are required.

The new functionality appears without modifying existing behavior. This is one of the greatest strengths of event-driven systems (complying with the Open-Closed Principle).

---

### The Costs of Event-Driven Systems

Nothing in software engineering is free. Event-driven architectures introduce new challenges:

1. **Harder Debugging:** Control flow becomes less obvious. Instead of a linear `A -> B -> C`, we have `A -> ??? -> B, C`. Understanding the execution path requires tracing events through the bus.
2. **Hidden Dependencies:** Although components no longer depend directly on each other's code, they still depend on _event names_. If a developer changes `message:received` to `message:new`, all subscribers will silently stop working.
3. **Event Storms:** Poorly designed systems may generate excessive, cascading events, creating performance bottlenecks and maintenance nightmares.

### Preparing for the Next Step

Event-Driven Architecture solved an important internal problem: **How can components communicate without knowing about one another?**

However, another challenge remains. Users interact with Isimud through explicit terminal commands:
`/connect-peer`, `/send-to`, `/help`.

How should these explicit actions be organized? Should they all live inside one giant `if/else` statement? Or is there a better, more scalable way?
To answer this question, we must explore one of the most practical design patterns in software engineering: **The Command Pattern**.
